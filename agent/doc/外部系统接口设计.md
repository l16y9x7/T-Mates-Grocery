# 外部系统接口设计

状态：设计稿

设计日期：2026-09-03

## 1. 接口说明

本文只定义外部系统与机器人系统之间的接口格式，不修改现有业务代码。外部系统只需要关注以下接口：

- 健康检查：判断系统当前是否可以接收任务。
- Task0 理货：触发机器人巡检并记录货架状态。
- Task1 取货：提交订单并触发机器人取货。
- Task2 补货：触发机器人检查货架并完成补货。
- 任务状态上报：机器人主动向外部系统上报所有任务的进度和结果。

三个任务均为异步执行。任务触发接口只返回“已受理”和 `task_run_id`，实际进度通过任务状态上报接口获取。Task0、Task1、Task2 同一时间只能执行一个任务。

## 2. 通用格式

- 协议：HTTPS，消息格式：`application/json`，字符集：UTF-8。
- 请求头：`Authorization`、`X-Request-Id`；任务触发接口还需要 `Idempotency-Key`。
- 时间：使用 ISO 8601 格式，例如 `2026-09-03T10:30:00+08:00`。
- 成功触发任务返回 `202 Accepted`，表示任务已登记，不代表机器人已经完成任务。
- 所有任务状态都包含 `task_run_id`、`task_type`、`task_name`、`status`、`current_step` 和 `summary`。

## 3. 接口总览

### 3.1 外部调用系统

| 编号 | 方向 | 方法 | 建议路径 | 用途 |
|---|---|---|---|---|
| 1 | 外部系统 → 机器人系统 | `GET` | `/api/external/v1/health` | 检查 Task0、Task1、Task2 是否可以触发 |
| 2 | 外部系统 → 机器人系统 | `POST` | `/api/external/v1/tasks/0/runs` | 异步触发 Task0 理货 |
| 3 | 外部系统 → 机器人系统 | `POST` | `/api/external/v1/task1/orders` | 提交订单并异步触发 Task1 取货 |
| 4 | 外部系统 → 机器人系统 | `POST` | `/api/external/v1/tasks/2/runs` | 异步触发 Task2 补货 |

### 3.2 系统主动上报外部

| 编号 | 方向 | 方法 | 地址 | 用途 |
|---|---|---|---|---|
| 5 | 机器人系统 → 外部系统 | `POST` | 外部提供的状态回调地址 | 上报所有 Task0、Task1、Task2 的受理、进度和最终结果 |

第五个接口不是机器人系统的入站路由，而是机器人系统向外部回调地址发起的 HTTP 请求。

### 3.3 输入输出速览

#### 3.3.1 健康检查

```http
GET /api/external/v1/health
Authorization: Bearer <external-access-token>
```

请求体：无。

成功响应示例：

```json
{
  "status": "READY",
  "accepting_tasks": true,
  "ready_for_task0": true,
  "ready_for_task1": true,
  "ready_for_task2": true,
  "active_task": null
}
```

`READY` 表示可以接收任务，`BUSY` 表示系统正常但当前有任务执行，`NOT_READY` 表示依赖或 Task2 前置数据未就绪。

请求体：

成功响应（`202 Accepted`）：

```json
{
  "external_task_id": "REPLENISH-20260903-0001",
  "task_run_id": "task2-20260903-103000-a1b2c3",
  "task_type": "TASK2_REPLENISHMENT",
```

#### 3.3.5 任务状态上报

机器人向外部回调地址发送：

```http
POST https://external.example.com/api/robot/task-status
Content-Type: application/json
Authorization: Bearer <callback-access-token>
```

请求体示例：

```json
{
  "task_run_id": "task1-20260903-103000-a1b2c3",
  "task_type": "TASK1_PICKUP",
  "task_name": "取货",
  "status": "RUNNING",
  "display_title": "正在为您取货",
  "display_message": "已取到 1 件商品，正在处理第 2 件商品",
  "current_step": {"code": "PICKING", "label": "正在取第 2 件商品", "progress_percent": 40},
  "summary": {"total_items": 2, "items_completed": 1, "items_in_progress": 1},
  "user_notice": {"level": "INFO", "message": "取货正在进行中，请稍候"}

```

外部处理成功返回任意 `2xx`。状态必须面向用户展示，Task0 使用“理货”，Task1 使用“取货”，Task2 使用“补货”，不展示内部端口、导航点、姿态或底层错误信息。

## 4. 通用约定

### 4.1 基础协议

- 协议使用 HTTPS；开发环境可以使用 HTTP。
- 请求和响应均使用 `application/json`。
- 字符编码统一使用 UTF-8。
- 时间字段使用 ISO 8601 格式并带时区，例如 `2026-09-03T10:30:00+08:00`。
- 所有响应都携带 `schema_version`，当前值为 `1.0`。

### 4.2 标识符

| 字段 | 说明 |
|---|---|
| `external_task_id` | 外部系统为 Task0/Task2 触发请求生成的业务任务号；Task1 建议直接使用订单号 |
| `external_order_id` | Task1 的外部业务订单号；Task0/Task2 不使用此字段 |
| `task_run_id` | 机器人系统生成的本次 Task0、Task1 或 Task2 运行 ID |
| `request_id` | 当前 HTTP 请求的链路 ID，用于排查接口问题 |
| `event_id` | 单次状态上报事件 ID，用于去重 |
| `sequence` | 同一 `task_run_id` 下单调递增的状态序号 |

建议的 `event_type` 枚举如下：

| `event_type` | 说明 |
|---|---|
| `TASK_ACCEPTED` | 任务已受理，尚未开始实际动作 |
| `TASK_PROGRESS` | 任务阶段或明细发生变化 |
| `TASK_HEARTBEAT` | 阶段未变化，仅用于刷新在线状态和更新时间 |
| `TASK_COMPLETED` | 任务成功完成或部分完成 |
| `TASK_FAILED` | 任务整体失败 |

`task_run_id` 必须出现在所有任务状态上报中；Task0/Task2 使用 `external_task_id`，Task1 同时使用 `external_task_id` 和 `external_order_id`。外部系统应以 `task_run_id + sequence` 或 `event_id` 去重，不应仅依赖时间戳判断新旧状态。

### 4.3 认证和签名

外部调用机器人系统时建议使用：

```http
Authorization: Bearer <external-access-token>
X-Request-Id: <request-id>
Idempotency-Key: <client-generated-key>
```

机器人系统向外部上报时建议使用：

```http
Authorization: Bearer <callback-access-token>
X-Event-Id: <event-id>
X-Task-Run-Id: <task-run-id>
X-Signature: sha256=<hmac-signature>
```

签名原文建议为：

```text
<timestamp>.<raw-json-body>
```

并增加 `X-Signature-Timestamp`，外部系统拒绝超过允许时间窗口的请求，避免回放攻击。

## 5. 接口一：系统健康检查

### 5.1 请求

```http
GET /api/external/v1/health
Authorization: Bearer <external-access-token>
X-Request-Id: health-20260903-0001
```

不需要请求体。

### 5.2 响应语义

健康检查需要区分“服务进程活着”和“当前可以执行指定任务”。整体状态用于判断系统是否可用，各任务状态用于判断 Task0、Task1、Task2 是否分别可以触发：

- `READY`：至少一个外部任务具备触发条件，且当前没有其他任务占用机器人。
- `BUSY`：依赖服务就绪，但当前已有任务执行，暂时不能触发新的任务。
- `NOT_READY`：任务依赖不可用，或 Task2 所需的 Task0 基准数据尚未生成。
- `ERROR`：健康检查本身无法完成，不能据此接单。

建议 HTTP 状态码：

| HTTP 状态码 | `status` | 说明 |
|---:|---|---|
| `200` | `READY` | 至少有一个任务可以触发 |
| `200` | `BUSY` | 系统正常但当前繁忙，外部应稍后重试 |
| `503` | `NOT_READY` | 依赖未就绪 |
| `503` | `ERROR` | 健康检查失败 |
| `401/403` | - | 认证失败或无权限 |

### 5.3 响应示例：可接单

```json
{
  "schema_version": "1.0",
  "request_id": "health-20260903-0001",
  "checked_at": "2026-09-03T10:30:00+08:00",
  "status": "READY",
  "ready_for_task0": true,
  "ready_for_task1": true,
  "ready_for_task2": true,
  "accepting_tasks": true,
  "active_task": null,
  "dependencies": [
    {
      "name": "task_orchestrator",
      "status": "READY",
      "latency_ms": 4
    },
    {
      "name": "navigation",
      "status": "READY",
      "latency_ms": 12
    },
    {
      "name": "pose",
      "status": "READY",
      "latency_ms": 8
    },
    {
      "name": "pick_place",
      "status": "READY",
      "latency_ms": 10
    },
    {
      "name": "sku",
      "status": "READY",
      "latency_ms": 15
    }
  ]
}
```

### 5.4 响应示例：执行中

```json
{
  "schema_version": "1.0",
  "request_id": "health-20260903-0002",
  "checked_at": "2026-09-03T10:31:00+08:00",
  "status": "BUSY",
  "ready_for_task0": false,
  "ready_for_task1": false,
  "ready_for_task2": false,
  "accepting_tasks": false,
  "active_task": {
    "task_type": "TASK1_PICKUP",
    "task_name": "取货",
    "task_run_id": "task1-20260903-103000-a1b2c3"
  },
  "dependencies": []
}
```

健康接口不建议返回机器人 IP、内部端口、下游 URL、当前商品名或抓取位姿，避免暴露内部拓扑和用户订单信息。

### 5.5 健康检查范围

Task0、Task1、Task2 的实际依赖如下：

- Task0：导航、姿态、头部相机。
- Task1：导航、姿态、`8086` pick-place、SKU 服务。
- Task2：导航、感知、姿态、`8086` pick-place、头部相机，以及 Task0 生成的 RGB-D 基准数据。

健康检查应按任务分别返回依赖明细，并额外检查统一编排服务、全局任务占用状态和 Task2 的基准数据前置条件。Task0 成功完成后才认为 Task2 具备触发条件。

## 6. 接口二：外部触发任务

三个任务都采用异步触发：接口只负责校验、登记和启动后台任务，成功后立即返回 `202 Accepted`。三个触发接口共用认证、幂等和全局机器人执行锁。

### 6.1 Task0：触发理货

#### 6.1.1 请求

```http
POST /api/external/v1/tasks/0/runs
Content-Type: application/json
Authorization: Bearer <external-access-token>
Idempotency-Key: preparation-20260903-0001
X-Request-Id: request-20260903-0002
```

请求体：

```json
{
  "external_task_id": "PREP-20260903-0001",
  "status_callback_url": "https://external.example.com/api/robot/task-status"
}
```

Task0 当前内部请求没有业务参数，外部请求中的 `external_task_id` 只用于幂等、状态关联和审计。对用户展示时，任务名称固定为“理货”，不要展示“基准采集”等内部术语。`status_callback_url` 未传时使用系统默认回调地址。

#### 6.1.2 执行内容

Task0 实际按配置执行：

1. 检查导航、姿态和头部相机。
2. 导航到 `start`。
3. 按配置顺序访问全部货架巡检点。
4. 在每个巡检点依次准备上下观察姿态并采集 RGB-D。
5. 校验并保存每个巡检点的 RGB、深度和元数据。
6. 完成后返回 `start`。

Task0 的成功条件是全部配置巡检点的上下视角采集成功，并成功返回开始点。生成的基准数据是 Task2 的必要前置条件。

按当前 Task0 实现，任意关键采集或收尾动作失败都会返回整体失败；`PARTIAL_SUCCESS` 只用于展示已经完成的采集进度，不能把不完整的基准数据标记为可供 Task2 使用。

#### 6.1.3 成功响应

HTTP 状态码：`202 Accepted`

```json
{
  "schema_version": "1.0",
  "request_id": "request-20260903-0002",
  "external_task_id": "PREP-20260903-0001",
  "task_run_id": "task0-20260903-103000-a1b2c3",
  "task_type": "TASK0_INVENTORY",
  "task_name": "理货",
  "status": "ACCEPTED",
  "accepted_at": "2026-09-03T10:30:00+08:00",
  "status_callback_enabled": true
}
```

### 6.2 Task1：提交订单并触发取货

#### 6.2.1 请求

```http
POST /api/external/v1/task1/orders
Content-Type: application/json
Authorization: Bearer <external-access-token>
Idempotency-Key: order-20260903-0001
X-Request-Id: request-20260903-0001
```

请求体建议如下：

```json
{
  "external_task_id": "ORD-20260903-0001",
  "external_order_id": "ORD-20260903-0001",
  "items": [
    {
      "sku_id": "SKU_001"
    },
    {
      "sku_id": "SKU_002"
    }
  ],
  "status_callback_url": "https://external.example.com/api/robot/task-status"
}
```

Task1 的 `external_task_id` 建议直接取值为 `external_order_id`，这样三个任务可以使用统一的状态关联字段。对用户展示时，任务名称固定为“取货”，不要展示“分拣”或底层 `SORTING`。

Task1 的每个订单项使用 `sku_id` 指定商品。机器人系统通过 SKU 服务的
`GET /sku/search_by_SKU?sku=<sku_id>` 查询标准商品名称、图片和货位，再交给现有 Task1
执行流程；外部系统不需要传入 `product_name`。

如果外部系统只有固定回调地址，也可以不传 `status_callback_url`，由机器人系统配置文件提供默认地址。按订单传入的回调地址必须经过白名单校验，不能允许任意 URL。

#### 6.2.2 当前版本订单约束

由于现有 Task1 的实际执行契约是两件商品，V1 订单必须满足：

- `items` 必须恰好包含两个元素。
- 两个 `sku_id` 必须非空且不能重复。
- 每件商品默认数量为 `1`；V1 不支持 `quantity > 1`。
- `sku_id` 必须存在于当前 SKU 服务商品目录，Agent 根据 SKU 目录解析商品名和货位。
- 商品必须能够解析出合法货位和至少一个可用抓取手/导航点。
- `external_order_id` 长度建议限制为 1-200 个字符。

如果后续需要支持多件同 SKU 商品，应先扩展 Task1 的订单模型和物理执行策略，不能仅在外部接口放宽校验。

#### 6.2.3 接受请求后的处理顺序

接口收到订单后建议按以下顺序处理：

1. 校验认证、请求格式、订单号和商品数量。
2. 检查幂等键和 `external_order_id` 是否已经受理。
3. 检查系统是否可以接单。
4. 生成 `task_run_id`，持久化订单和初始状态。
5. 将订单转换成现有 Task1 所需的两个商品名和订单号。
6. 通过统一任务协调器以后台任务方式启动 Task1。
7. 立即返回 `202 Accepted`。
8. 发送第一条 `ACCEPTED` 状态上报。

下单接口不应同步等待机器人完整执行结束。当前内部 `POST /tasks/1/run` 是同步等待型接口；外部接口需要在其外层使用后台任务启动能力，避免外部 HTTP 请求被机器人动作时间占满。

#### 6.2.4 成功响应

HTTP 状态码：`202 Accepted`

```json
{
  "schema_version": "1.0",
  "request_id": "request-20260903-0001",
  "external_task_id": "ORD-20260903-0001",
  "external_order_id": "ORD-20260903-0001",
  "task_run_id": "task1-20260903-103000-a1b2c3",
  "task_type": "TASK1_PICKUP",
  "task_name": "取货",
  "status": "ACCEPTED",
  "accepted_at": "2026-09-03T10:30:00+08:00",
  "status_callback_enabled": true
}
```

Task0 和 Task2 的受理响应使用 `external_task_id`；Task1 的受理响应同时返回 `external_task_id` 和 `external_order_id`。三个接口的 `task_run_id` 都是后续状态回调和任务查询的主关联键。

#### 6.2.5 重复请求

建议同时支持两种幂等判断：

- 相同 `Idempotency-Key`：必须返回第一次请求的相同受理结果，不得再次启动任务。
- 相同 `external_order_id`：
  - 如果订单内容完全一致，返回原来的 `task_run_id` 和当前状态摘要。
  - 如果订单内容不同，返回冲突，不得覆盖原订单。

重复请求的推荐响应：

```json
{
  "schema_version": "1.0",
  "request_id": "request-20260903-0001-retry",
  "external_order_id": "ORD-20260903-0001",
  "task_run_id": "task1-20260903-103000-a1b2c3",
  "task_type": "TASK1_PICKUP",
  "task_name": "取货",
  "status": "ACCEPTED",
  "duplicate": true
}
```

#### 6.2.6 下单错误

| HTTP 状态码 | `error_code` | 说明 |
|---:|---|---|
| `400` | `INVALID_ORDER` | 请求结构或字段格式错误 |
| `401/403` | `UNAUTHORIZED` / `FORBIDDEN` | 认证或权限失败 |
| `409` | `TASK_BUSY` | 机器人当前已有任务执行 |
| `409` | `ORDER_CONFLICT` | 相同订单号但订单内容不一致 |
| `422` | `ORDER_NOT_SUPPORTED` | 不是恰好两个不同商品，或包含不支持的数量 |
| `422` | `PRODUCT_NOT_FOUND` | 商品不在当前 SKU 商品池 |
| `422` | `PRODUCT_SLOT_INVALID` | 商品无法解析到合法货位 |
| `503` | `SYSTEM_NOT_READY` | Task1 依赖未就绪 |
| `500` | `ORDER_ACCEPT_FAILED` | 订单持久化或后台任务启动失败 |

错误响应统一采用：

```json
{
  "schema_version": "1.0",
  "request_id": "request-20260903-0001",
  "error_code": "TASK_BUSY",
  "message": "当前有任务正在执行，请稍后重试",
  "retryable": true
}
```

### 6.3 Task2：触发补货

#### 6.3.1 请求

```http
POST /api/external/v1/tasks/2/runs
Content-Type: application/json
Authorization: Bearer <external-access-token>
Idempotency-Key: shortage-20260903-0001
X-Request-Id: request-20260903-0003
```

请求体：

```json
{
  "external_task_id": "SHORTAGE-20260903-0001",
  "status_callback_url": "https://external.example.com/api/robot/task-status"
}
```

Task2 当前内部请求没有商品参数。任务会根据 Task0 理货生成的货架数据和现场巡检结果自动发现缺货商品，再按照当前配置完成补货。因此外部系统只需要提供任务号和可选回调地址。对用户展示时，任务名称固定为“补货”，不要展示“SHORTAGE”或“缺货检测任务”。

#### 6.3.2 前置条件

- Task0 必须已经成功完成，并且基准 RGB-D 数据完整可读。
- 当前不能有 Task0、Task1、Task2 或 Task3 占用机器人。
- 导航、感知、姿态、`8086` pick-place 和头部相机必须就绪。

如果 Task0 尚未成功，Task2 触发接口返回 `503 SYSTEM_NOT_READY`，不创建新的 Task2 运行。

#### 6.3.3 执行内容

Task2 实际按以下流程执行：

1. 检查依赖服务和 Task0 基准数据。
2. 按配置巡检点和上下观察姿态检查货架。
3. 识别缺货商品并按货位去重。
4. 查询商品标准货位，规划安全抓取手和目标巡检点。
5. 前往补货台，准备补货台抓取姿态并抓取候选商品。
6. 返回对应货架，准备货架放置姿态并完成放置。
7. 对失败候选继续尝试后续候选；成功完成两件补货后结束本轮业务处理。
8. 导航到任务判定区；必要时按现有策略回到开始点。

Task2 的待处理商品在巡检后才能确定，因此状态上报中的 `items` 初始可以为空；发现商品后再逐步补充商品级状态。

#### 6.3.4 成功响应

HTTP 状态码：`202 Accepted`

```json
{
  "schema_version": "1.0",
  "request_id": "request-20260903-0003",
  "external_task_id": "SHORTAGE-20260903-0001",
  "task_run_id": "task2-20260903-103000-d4e5f6",
  "task_type": "TASK2_REPLENISHMENT",
  "task_name": "补货",
  "status": "ACCEPTED",
  "accepted_at": "2026-09-03T10:30:00+08:00",
  "status_callback_enabled": true
}
```

#### 6.3.5 触发错误

除通用错误外，Task2 还可能返回：

| HTTP 状态码 | `error_code` | 说明 |
|---:|---|---|
| `409` | `TASK_BUSY` | 当前已有任务执行 |
| `422` | `TASK2_NOT_SUPPORTED` | 当前配置无法完成 Task2 |
| `503` | `BASELINE_NOT_READY` | Task0 基准数据不存在或不完整 |
| `503` | `SYSTEM_NOT_READY` | Task2 依赖服务未就绪 |

#### 6.4 三个触发接口的通用幂等规则

- 相同 `Idempotency-Key` 必须返回第一次触发的相同受理结果，不得重复启动 Task0、Task1 或 Task2。
- 相同 `external_task_id` 必须绑定同一个任务类型和请求内容；内容不一致时返回 `409 TASK_CONFLICT`。
- 任务已经结束时，重复请求返回原 `task_run_id` 和最终状态摘要，不重新执行机器人动作。
- 任务处于 `BUSY` 时返回 `409 TASK_BUSY`；外部系统可以在健康检查恢复为可触发后重新提交。

## 7. 接口三：任务状态主动上报

### 7.1 上报方式

Task0、Task1、Task2 共用同一个状态回调协议，机器人系统向外部系统发起：

```http
POST https://external.example.com/api/robot/task-status
Content-Type: application/json
Authorization: Bearer <callback-access-token>
X-Event-Id: evt-task1-20260903-0008
X-Task-Run-Id: task1-20260903-103000-a1b2c3
X-Signature-Timestamp: 2026-09-03T10:30:08+08:00
X-Signature: sha256=<signature>
```

外部系统收到状态后，成功处理应返回任意 `2xx`，建议响应：

```json
{
  "received": true,
  "event_id": "evt-task1-20260903-0008"
}
```

非 `2xx` 或请求超时都视为上报失败，机器人系统需要重试。

### 7.2 状态上报数据结构

所有 Task0、Task1、Task2 都必须上报状态，不能只有 Task1 上报。状态回调使用统一外层结构，具体的用户展示内容根据 `task_type` 填充。

外部系统至少应展示以下信息：

- **任务名称**：理货、取货或补货。
- **任务总状态**：已接收、执行中、已完成、部分完成或失败。
- **当前动作**：用一句用户能理解的话说明机器人正在做什么。
- **进度**：阶段进度和已完成数量；进度是展示用估算值，不代表精确耗时。
- **当前位置**：起点、货架、交付台、补货台或任务判定区。
- **任务明细**：Task0 展示巡检点和采集视角，Task1 展示订单商品，Task2 展示发现的缺货商品及补货结果。
- **下一步**：告诉用户机器人接下来要做什么。
- **用户提示**：成功、等待、重试、部分完成和人工检查等提示。

状态载荷中的明细字段按任务类型使用：

- Task0 使用 `captures` 展示各巡检点、上下视角和采集结果；`items` 可以省略或为空。
- Task1 使用 `items` 展示订单中的两件商品；`captures` 可以省略。
- Task2 在发现缺货后使用 `items` 展示缺货商品、补货抓取和货架放置结果；巡检完成前 `items` 可以为空。
- `external_order_id` 仅对 Task1 必填，Task0/Task2 不传或传 `null`。

三类任务的状态上报要求如下：

| 任务 | 必须上报的开始状态 | 必须上报的过程状态 | 必须上报的结束状态 |
|---|---|---|---|
| Task0 理货 | `ACCEPTED`：已接收理货任务 | 每个货架区域、上层/下层记录进度 | `SUCCEEDED` / `FAILED` |
| Task1 取货 | `ACCEPTED`：已接收取货订单 | 每件商品的寻找、取货和交付进度 | `SUCCEEDED` / `PARTIAL_SUCCESS` / `FAILED` |
| Task2 补货 | `ACCEPTED`：已接收补货任务 | 巡检、发现缺货、取补货商品和放回货架进度 | `SUCCEEDED` / `PARTIAL_SUCCESS` / `FAILED` |

任何任务都不能只上报最终结果。即使任务很快失败，也至少需要上报一条 `TASK_ACCEPTED` 和一条 `TASK_FAILED`，并在失败状态中说明用户下一步应该等待重试还是联系工作人员。

为了便于外部页面直接展示，`display_title`、`display_message`、`current_step.label`、`next_step.label`、`user_notice.message` 应由机器人系统生成完整中文文案。外部系统不需要根据底层事件名自行翻译。

`task_type` 的对外枚举固定为：

| `task_type` | `task_name` | 用户理解 |
|---|---|---|
| `TASK0_INVENTORY` | `理货` | 机器人正在巡检并记录货架状态 |
| `TASK1_PICKUP` | `取货` | 机器人正在根据订单取商品 |
| `TASK2_REPLENISHMENT` | `补货` | 机器人正在把缺货商品补回货架 |

外部任务类型与现有内部任务类型的映射如下：

| 外部 `task_type` | 现有内部 `task_type` | 说明 |
|---|---|---|
| `TASK0_INVENTORY` | `PREPARATION` | 对外称为理货，内部用于生成货架状态基础数据 |
| `TASK1_PICKUP` | `SORTING` | 对外称为取货，内部沿用现有取放任务类型 |
| `TASK2_REPLENISHMENT` | `SHORTAGE` | 对外称为补货，内部沿用现有缺货补货任务类型 |

### 7.3 顶层任务状态

| `status` | 用户展示 | 含义 |
|---|---|---|
| `ACCEPTED` | 已接收任务 | 任务已经接收，准备启动 |
| `RUNNING` | 执行中 | 任务正在执行，具体进度看 `current_step` |
| `SUCCEEDED` | 已完成 | 任务满足对应类型的完整成功条件 |
| `PARTIAL_SUCCESS` | 部分完成 | 任务流程已结束，但部分采集、补货或订单商品未完成 |
| `FAILED` | 执行失败 | 任务无法正常完成，且不是可接受的部分完成 |
| `CANCELLED` | 已取消 | 任务被系统或管理端取消；本期如不开放取消操作，可暂不使用 |

当前 Task0、Task1、Task2 的内部结果都可能使用 `status="SUCCEEDED"` 表示编排流程已收尾，外部状态适配层必须结合任务类型和明细重新计算用户状态：

- Task0：全部配置巡检点的上下视角采集成功并返回开始点，外部 `SUCCEEDED`；当前实现只完成部分采集时外部 `FAILED`，并在明细中保留已完成采集数量。
- Task1：两件订单商品均 `placed=true`，外部 `SUCCEEDED`；至少一件完成但不是两件，外部 `PARTIAL_SUCCESS`。
- Task2：完成全部巡检且未发现缺货，或完成当前发现的补货目标并收尾，外部 `SUCCEEDED`；只完成部分补货，外部 `PARTIAL_SUCCESS`。
- Task1/Task2 没有完成放置但仍有确认持有商品时，外部使用 `PARTIAL_SUCCESS`，并在 `items` 和 `summary.held_items` 中明确展示。
- 健康检查失败、任务收尾导航失败、启动失败或未捕获异常：外部 `FAILED`。

### 7.4 面向用户的主流程状态

外部状态只保留用户可理解的阶段，不直接暴露内部事件名。不同任务使用各自的阶段集合；公共阶段 `ACCEPTED`、`HEALTH_CHECKING`、`FINISHING`、`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED` 的语义保持一致。

状态回调发送的是“当前完整状态快照”，不是只包含变化字段的增量消息。外部页面收到任意一条有效状态后，都可以直接覆盖本地任务卡片；不需要依赖前一条消息才能正确展示。

#### 7.4.1 Task0 理货

| `current_step.code` | `label` | 进入时机 | 建议进度 |
|---|---|---|---:|
| `ACCEPTED` | 已接收任务 | Task0 请求受理完成 | 0% |
| `HEALTH_CHECKING` | 正在检查设备 | 开始检查导航、姿态和相机 | 5% |
| `NAVIGATING_TO_START` | 正在前往起点 | 开始前往 `start` | 10% |
| `INSPECTING` | 正在巡检货架 | 开始访问某个巡检点 | 15%-25% |
| `CAPTURING` | 正在记录货架信息 | 正在记录某个巡检点的上下视角货架数据 | 25%-85% |
| `RETURNING_TO_START` | 正在返回起点 | 全部采集完成后返回 `start` | 95% |
| `SUCCEEDED` | 理货完成 | 全部货架信息记录成功并返回起点 | 100% |
| `PARTIAL_SUCCESS` | 理货部分完成 | 部分货架信息已记录，但仍有未完成区域 | 100% |

Task0 状态中的 `summary` 建议包含：

```json

  "captures_total": 10,
  "captures_completed": 4,
  "captures_failed": 0

```

`captures` 建议按巡检点和观察视角展示，每项包含 `target_id`、`view`（`UPPER`/`LOWER`）、`status` 和用户提示。具体采集文件路径不作为用户状态必需字段。

### 7.4.4 用户展示字段规则

状态回调建议始终提供以下用户展示字段；即使任务刚开始、还没有发现商品，也应提供完整的任务名称、当前动作和提示：

| 字段 | 必填 | 展示用途 |
|---|---|---|
| `task_name` | 是 | 展示“理货”“取货”或“补货” |
| `display_title` | 是 | 页面主标题，例如“正在为您取货” |
| `display_message` | 是 | 当前状态的一句话说明 |
| `current_step` | 是 | 当前阶段、阶段进度和动作说明 |
| `next_step` | 建议 | 预计下一步动作；任务结束时为 `null` |
| `location` | 是 | 当前业务位置，如货架区域、交付台 |
| `summary` | 是 | 数量统计和总体进度 |
| `user_notice` | 是 | 用户提示级别、提示码和可读文案 |
| `last_updated_at` | 是 | 页面判断状态是否过期的时间 |

`display_title` 和 `display_message` 应优先描述“机器人为用户做了什么”，不要描述内部实现。例如：

| 场景 | 推荐展示 | 不推荐展示 |
|---|---|---|
| Task0 | `正在巡检并记录货架状态` | `正在采集 RGB-D` |
| Task1 | `正在为您取可口可乐罐装` | `正在调用 /pick` |
| Task2 | `发现 2 件商品需要补货` | `SHORTAGE finding=2` |
| 动作重试 | `第一次操作未完成，正在重新尝试` | `ACTION_RESULT_UNKNOWN` |

### 7.5 商品级状态

Task1 的订单商品和 Task2 已发现的缺货商品建议使用以下状态：

| 状态 | 用户展示 | 说明 |
|---|---|---|
| `PENDING` | 等待处理 | 尚未开始处理 |
| `LOCATING` | 正在定位 | 正在解析货位或前往货架 |
| `PICKING` | 正在取货 | 正在执行取货动作 |
| `PICKED` | 已取到 | 已确认商品在手上 |
| `PLACING` | 正在交付 | 正在将商品放到交付台或目标货架 |
| `PLACED` | 已完成放置 | 已确认商品完成交付或补回货架 |
| `PICK_FAILED` | 取货失败 | 取货失败且未确认拿到商品 |
| `PLACE_FAILED` | 放置失败 | 商品已取到但放置未完成 |
| `HELD` | 商品仍在手上 | 任务结束时仍确认商品未放下 |
| `UNKNOWN` | 状态待确认 | 动作结果无法确认，相关手臂已被保护性锁定 |
| `SKIPPED` | 未处理 | 因配置策略、前置失败或不可用而跳过 |

Task2 可以额外使用 `SHORTAGE_FOUND`（已发现缺货）和 `REPLENISHED`（已完成补货）作为更具体的用户状态；如果外部系统希望减少枚举，也可以分别映射为 `PENDING` 和 `PLACED`，但必须通过 `message` 说明“缺货”或“已补货”。

对用户展示时，优先使用 `status_label` 和 `message`。`UNKNOWN` 不应展示为“成功”，应明确提示“动作结果待确认，请人工检查”。

### 7.6 位置展示

位置只用于帮助用户理解流程，建议使用抽象业务位置：

| `location.code` | `label` |
|---|---|
| `START` | 起点 |
| `SHELF` | 货架区域 |
| `DELIVERY_TABLE` | 交付台 |
| `TASK_BOUNDARY` | 任务判定区 |
| `UNKNOWN` | 位置未知 |

默认不向外部展示具体导航点 ID，例如 `H12_INSPECT`，除非外部业务确实需要定位机器人。即使展示，也应作为可选字段，不作为用户状态判断依据。

## 8. 状态上报时机

建议在以下时机立即上报：

1. 所有任务受理：发送 `TASK_ACCEPTED`，展示“已接收理货/取货/补货任务”。
2. 所有任务开始和完成健康检查：展示“正在检查设备”，不要展示具体服务名称。
3. Task0 理货：开始前往起点、每个货架区域到达、每个上下视角开始/完成记录、返回起点。
4. Task1 取货：订单确认、商品定位、取每件商品、商品取到、前往交付台、每件商品交付完成。
5. Task2 补货：开始检查货架、每个货架区域完成、确认缺货、规划补货、前往补货台、取补货商品、返回目标货架、补回商品。
6. 所有任务进入任务判定区或返回起点收尾。
7. 所有任务最终发送 `TASK_COMPLETED` 或 `TASK_FAILED`；部分完成使用 `TASK_COMPLETED` 搭配 `status=PARTIAL_SUCCESS`。

对于一次可能持续几十秒的导航、姿态准备或抓取动作，建议每 5 秒发送一次相同阶段的心跳状态，并更新 `occurred_at`。心跳事件也占用 `sequence`，但不需要改变 `current_step.code`。

如果状态回调暂时失败，不应阻塞机器人动作。状态事件应先写入本地可靠队列或事件文件，再由独立上报任务重试。

## 9. 回调可靠性和顺序

### 9.1 重试策略

建议对回调使用指数退避：

```text
第 1 次失败：1 秒后
第 2 次失败：2 秒后
第 3 次失败：4 秒后
第 4 次失败：8 秒后
第 5 次失败：16 秒后
```

单个事件建议最多自动重试 5 次；超过次数进入待补偿队列并记录告警。最终状态事件的重试优先级高于中间心跳事件。

### 9.2 去重和乱序

外部系统必须：

- 以 `event_id` 去重。
- 对相同 `task_run_id` 只接受更大的 `sequence`。
- 允许网络重试造成相同事件重复到达。
- 对晚到的旧状态不覆盖已经展示的新状态。

机器人系统也应保留已上报事件的结果，避免回调方返回超时后重复生成不同的事件 ID。

### 9.3 回调失败不影响任务结果

外部状态上报失败只代表“外部暂时没有收到状态”，不代表机器人任务失败。机器人任务是否成功仍由对应 Task0、Task1 或 Task2 的实际执行结果决定。最终状态事件必须持久化，便于人工补发或后续补偿。

```text
   |                                  |                                  |

   |<--------- 200 READY -------------|                                  |
   |                                  |                                  |
   |-- POST /api/external/v1/task1/orders ->|                              |
   |<--------- 202 ACCEPTED -----------|                                  |
   |                                  |-- POST task-status: ACCEPTED ----->|
   |                                  |                                  |
   |                                  |-- Task1 健康检查、订单解析          |
   |                                  |-- POST task-status: RUNNING ------>|
   |                                  |                                  |
   |                                  |-- 货架导航、抓取、交付台放置        |
```

如果当前已有任务，任一触发接口都直接返回 `409 TASK_BUSY`，不创建新的 `task_run_id`，也不发送 `TASK_ACCEPTED` 状态。Task2 还必须在 Task0 理货数据就绪后才能触发。

## 12. 推荐实现拆分

后续落地时建议新增独立的外部接口适配层，不直接修改底层动作接口：

1. `ExternalHealthService`：封装依赖检查、Task0 基准数据检查和接单状态判断。
2. `ExternalTaskTriggerService`：负责 Task0、Task1、Task2 的请求校验、幂等、持久化和后台启动。
3. `TaskUserStatusProjector`：将三类任务的内部事件和最终结果转换成用户状态。
4. `ExternalStatusReporter`：负责签名、发送、重试、去重和最终事件补偿。
5. 任务与状态存储：至少保存任务类型、外部任务号/订单号、`task_run_id`、当前状态、`sequence`、回调事件和回调结果。

现有代码需要重点适配的地方：

- 现有 `Task0Request` 和 `Task2Request` 没有业务字段，外部触发请求中的任务号只用于幂等、状态关联和审计。
- 现有 `Task1Request` 以两个商品名和订单号承载模拟订单，外部接口需要先用 `items[].sku_id` 查询 SKU 目录，再转换为商品名。
- 现有统一协调器已经有后台任务启动能力，可以作为三个外部触发接口的异步执行基础。
- 现有三类任务日志事件包含底层细节，需要增加面向用户的状态投影，不应直接把 `events.jsonl` 原样发送给外部。
- 现有 Task0/Task1/Task2 结果固定使用内部 `status="SUCCEEDED"`，外部接口必须根据采集结果、`target_items[].picked/placed`、`held_items` 和 Task2 补货目标重新计算外部状态。
- 现有单进程全局执行锁需要在触发接口和健康接口中统一体现，避免健康检查显示可触发但提交时才发现冲突。

## 13. 验收标准

- 外部系统只依赖一个健康检查接口、三个任务触发接口和一个状态回调协议，不需要访问任何内部端口。
- 健康检查能正确区分可接单、执行中、依赖未就绪和检查异常。
- Task0、Task1、Task2 的重复触发不会产生第二次物理任务。
- 三个触发接口都在任务受理后立即返回，不等待机器人完整动作结束。
- 外部能够看到 Task0 的理货进度、Task1 的取货进度、Task2 的巡检和补货进度。
- Task1 两件商品、Task2 已发现的缺货商品可以分别展示，不因一件失败而丢失其他商品的结果。
- 网络重试不会造成重复物理动作，也不会导致外部状态倒退。
- 回调失败不阻塞机器人任务，并且最终状态可以补偿发送。
- 外部状态中不包含内部 IP、端口、原始堆栈、幂等动作键和不必要的视觉/位姿数据。
